# Веб-приложение UtrIskra

Панель управления генерацией и публикацией: расписание, ручной запуск,
галерея, история промптов и логи запусков. Заменяет запуск раннеров по
cron — планировщик (APScheduler) живёт внутри приложения.

**Адрес:** `http://192.168.0.58:8090` (доступ из локальной сети, без авторизации).

## Возможности

- **Дашборд** — карточки всех задач: тумблер расписания, время запуска
  (по времени сервера, UTC), кнопка «Запустить» (с подтверждением — результат
  публикуется в Telegram), ссылка ⚙ на настройки задачи, статус и время
  последнего запуска, ближайший запуск. Обновляется каждые 5 секунд.
- **Настройки задачи** (`/jobs/{key}`) — промпт (системный + пользовательский,
  хранится в БД с версионированием: каждое изменение — новая версия в таблице
  `job_prompts`), LLM-провайдер и температура, image-провайдер и его параметры
  (форма строится по `param_schema`), водяной знак, ретраи и chat_id публикации.
- **Провайдеры** (`/providers`) — инстансы LLM и генераторов изображений:
  проверка доступности (health), редактирование конфигов, цепочка LLM-fallback.
- **Архив задач** — неиспользуемая задача убирается в архив со страницы
  настроек (`POST /api/jobs/{key}/archive`): скрывается с дашборда, снимается
  с расписания, ручной запуск блокируется; изображения остаются в галерее
  и истории (фильтр помечает её «(архив)»). Вернуть — из свёрнутого блока
  «Архив» внизу дашборда, время расписания при этом сохраняется
  (но остаётся выключенным до явного включения).
- **Debug-режим публикаций** — отдельный бот и чат из `.env`
  (`DEBUG_TELEGRAM_TOKEN`, `DEBUG_TARGET_CHAT_ID`), два уровня:
  - глобальный тумблер «🐞 debug-чат» на дашборде (`POST /api/debug`) —
    ВСЕ публикации пайплайна идут в отладочный чат, на всех страницах
    горит пульсирующий бейдж «🐞 DEBUG»;
  - флаг задачи «Debug-публикация» в её настройках — только эта задача
    публикуется в отладочный чат (🐞 на карточке), удобно отлаживать
    промпт одной задачи, пока остальные работают в боевой канал.

  Действует правило «любой из уровней» — в debug-чате оказывается всё,
  что помечено хоть одним флагом; per-job `chat_id` при этом игнорируется.
  Включение без заполненных `DEBUG_*` отклоняется (400), публикация
  падает с ошибкой — в боевой канал случайно ничего не уйдёт.
- **Галерея** — все изображения/видео из `storage/images` с фильтром по
  генератору (принадлежность определяется по префиксу имени файла).
- **История** — записи из SQLite с поиском по тексту промпта; детальная
  страница показывает все три промпта и медиафайл.
- **Запуски** — история запусков (до 200) с логами каждого запуска.
- **Логи** (`/logs`) — два режима: «всё приложение» (журнал сервиса
  `storage/webapp/app.log`, ротация 5 МБ × 3: планировщик, ошибки вне
  запусков, старт/миграции) и **журнал конкретной задачи** — логи её
  последних 1–10 запусков (по умолчанию 3), собранные из истории
  `runs.jsonl` с маркерами начала/итога каждого запуска. Фильтр по уровню
  и тексту, автообновление каждые 5 с; со страницы настроек задачи ведёт
  ссылка «Логи задачи». uvicorn.access в файл не пишется (шум поллинга) —
  полный вывод по-прежнему в `journalctl -u utriskra-web`.

## Архитектура провайдеров и задач

Подробно — в `architecture-providers.md`. Кратко: задачи описаны в
`storage/webapp/jobs.json` (13 задач пайплайна `image`, включая MidJourney
с кропом сетки, + `midjourney_video` + `best_image_video`), провайдеры —
в `storage/webapp/providers.json` (секретов нет — только имена
env-переменных), промпты — в SQLite (таблица `job_prompts`, версия на каждое
изменение). Исполнение — `core/pipeline.py`: промпт из БД (+плейсхолдеры) →
цепочка LLM → image-провайдер → водяной знак → SQLite → Telegram; у видео-
пайплайнов свои этапы (кадр → публикация → видео; best-of: выбор популярного
фото по реакциям через Telethon за настраиваемый период → CDN → видео).
CLI-запуск задачи: `python -m core.run <ключ>`.

## Пакетная заготовка промптов

Anthropic Message Batches API считает токены вдвое дешевле, но отвечает не
сразу (обычно в пределах часа, максимум сутки). Расписание известно заранее,
поэтому тексты для ближайших запусков можно заказать пакетом
(`core/prompt_batches.py`).

**Включение** — в конфиге LLM-инстанса типа `anthropic` на странице
«Провайдеры» (перезапуск не нужен):

```json
{"type": "anthropic", "model": "claude-opus-5-5", "effort": "high",
 "batch": true, "batch_lead_minutes": 120, "batch_horizon_minutes": 360}
```

Режим действует, только если этот инстанс стоит **первым** в цепочке задачи
(общая `llm_chain` или провайдер, выбранный у задачи). Без флага всё работает
как раньше.

**Как работает.** Служебное задание планировщика раз в 5 минут (в отдельном
потоке, на дашборде не показывается):

1. опрашивает отправленные пакеты; завершённый разбирает по `custom_id` —
   готовые тексты становятся заготовками, а отказ модели, обрыв по
   `max_tokens`, ошибка и просрочка — нет (причина пишется в журнал);
2. списывает заготовки, не понадобившиеся за 12 часов после планового времени,
   и те, у чьей задачи с тех пор изменили промпт; записи старше 3 суток удаляет;
3. когда до ближайшего ещё не подготовленного запуска остаётся не больше
   `batch_lead_minutes`, отправляет **один** пакет на все включённые в
   расписании задачи (пайплайны `image` и `midjourney_video`), чей запуск
   попадает в окно от «сейчас + 10 минут» до «сейчас + `batch_horizon_minutes`».
   На запуск, для которого уже есть заготовка или отправленный запрос, второй
   раз ничего не шлётся.

При запуске задача берёт заготовку, если та готова, ещё не использована,
время запуска — от (плановое − lead − 30 минут) до (плановое + 12 часов) и
версия промпта не менялась; в историю попадают те system/user, по которым
модель писала текст. Иначе — обычная цепочка LLM. Ручной запуск из панели
в этом окне тоже забирает заготовку.

При расписании 04:30–07:30 и значениях по умолчанию пакет на все утренние
запуски уходит около 02:30 (время сервера, UTC).

**Журнал** (страница «Логи», всё приложение): «Отправлен пакет … : hidream на
18.11 04:30, …», «Пакет … завершён: готово N, отказов M, шёл K мин, токены…»,
«Пакетная заготовка … просрочена / отброшена: промпт задачи с тех пор
изменился»; в логе запуска задачи — «промпт взят из пакетной заготовки (пакет …)».

**Состояние** — `storage/webapp/prompt_batches.json`, переживает перезапуск.
Битый файл откладывается как `prompt_batches.json.broken-…`. Любой сбой
механизма (нет сети, ошибка API) — только предупреждение: задача запустится
обычной цепочкой. Неудачная отправка пакета повторяется не чаще раза в 15 минут.

**Руками:**

```bash
python -m core.prompt_batches status              # пакеты и заготовки
python -m core.prompt_batches tick                # один проход, как у планировщика
python -m core.prompt_batches submit zimage qwen  # отправить пакет сейчас (флаг не нужен)
python -m core.prompt_batches poll                # опросить отправленные пакеты
python -m unittest tests.test_prompt_batches      # самопроверка без сети
```

`submit` готовит заготовку на ближайший запуск задачи по расписанию (если
расписание выключено — на «сейчас»).

**Чего ждать от денег.** Если пакет не успел к запуску, задача идёт
синхронным вызовом по полной цене, а пакетный ответ всё равно оплачивается —
поэтому `batch_lead_minutes` не стоит делать меньше часа. В пакетном запросе
нет серверного fallback при отказе классификатора (API запрещает `fallbacks`
в пакетах) — такой запуск тоже уйдёт в синхронную цепочку.

## Важные особенности

- **После первой установки все расписания выключены** — включаются
  тумблером на дашборде.
- **Промпты живут в SQLite** и переезжают вместе со `storage/`. На полностью
  свежей установке (без `storage/`) промпты задаются в настройках задач
  вручную — файлов-исходников в репозитории больше нет (история в git).
- Расписание хранится в `storage/webapp/schedule.json`, история запусков —
  в `storage/webapp/runs.jsonl`.
- Каждый запуск выполняется в отдельном потоке со своим event loop,
  поэтому синхронные вызовы (LLM, MidJourney-сервис) не блокируют интерфейс.
- Статус запуска определяется по исключениям пайплайна и записям уровня
  ERROR в логе за время выполнения.
- Одновременный повторный запуск одного генератора блокируется (409);
  лимит одного запуска — 2 часа.
- Приложение должно работать строго **в один процесс** (внутри планировщик).

## Эксплуатация (systemd)

Юнит: `deploy/utriskra-web.service` → `/etc/systemd/system/utriskra-web.service`.

```bash
systemctl status utriskra-web          # статус
journalctl -u utriskra-web -f          # логи
sudo systemctl restart utriskra-web    # перезапуск (после обновления кода)
```

Переустановка юнита после правок файла:

```bash
sudo cp deploy/utriskra-web.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl restart utriskra-web
```

Хост/порт настраиваются переменными `WEB_HOST` / `WEB_PORT` в `.env`
(по умолчанию `0.0.0.0:8090`).

Запуск вручную (без systemd): `python run_web.py`.

## API

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/status` | статусы задач, расписание, последние запуски |
| POST | `/api/run/{key}` | запустить задачу (202; 409 — уже выполняется) |
| POST | `/api/schedule/{key}` | `{"enabled": bool, "hour": 0-23, "minute": 0-59}` |
| GET | `/api/runs?limit=50` | история запусков |
| GET | `/api/runs/{run_id}/logs` | лог запуска (text/plain) |
| GET | `/api/logs?lines=300&level=ERROR&q=&job=&runs=3` | журнал приложения или задачи (`job` = ключ, `runs` = число последних запусков) |
| POST | `/api/jobs/{key}` | сохранить настройки задачи (prompt/llm/image/watermark/publish) |
| POST | `/api/providers/{kind}/{name}` | сохранить конфиг провайдера (`kind`: llm/image) |
| POST | `/api/providers/{kind}/{name}/health` | проверка доступности провайдера |
| POST | `/api/providers/llm-chain` | цепочка LLM-fallback `{"chain": ["gemini", ...]}` |

Ключи задач — в `storage/webapp/jobs.json` (`stability`, `kandinsky`,
`midjourney`, `dalle`, `flux`, `yandex`, `gemini_image`, `midjourney_video`,
`best_image_video`, `zimage`, `stability_prompts`, `qwen`, `qwen_chat`,
`ernie`, `hidream`).

## Структура

```
providers/
├── llm/                 # base, gemini (ротация ключей), openai_compat (Ollama/vLLM/Qwen2API/...),
│                        # anthropic_claude (Claude: синхронный вызов и пакетный API)
└── image/               # base, images_api (qwen/zimage/ernie/hidream — единый шлюз br-01),
                         # stability, dalle, flux, kandinsky, yandex, gemini_image, qwen_chat
core/
├── pipeline.py          # пайплайны: image / midjourney_video / best_image_video
├── jobs.py              # jobs.json (задачи)
├── prompts.py           # промпты задач в SQLite (job_prompts, версионирование)
├── prompt_batches.py    # пакетная заготовка промптов (Anthropic Message Batches), CLI
├── providers_store.py   # providers.json (инстансы провайдеров, llm_chain)
├── publisher.py         # Telegram-публикация с ретраями
└── run.py               # CLI: python -m core.run <ключ задачи>
webapp/
├── app.py               # FastAPI-приложение, lifespan (БД, логи, планировщик)
├── routes.py            # страницы (Jinja2) и JSON API
├── registry.py          # реестр для панели — строится из jobs.json
├── schedule_store.py    # расписание в storage/webapp/schedule.json
├── scheduler_service.py # APScheduler, задачи включаются/выключаются из UI; тик заготовки промптов
├── task_manager.py      # фоновые запуски, сбор логов, история runs.jsonl
├── db.py                # чтение SQLite для галереи/истории
├── state.py             # singleton-объекты
├── templates/           # base, dashboard, gallery, history, history_detail, runs,
│                        # providers, job_settings
└── static/              # style.css, app.js
run_web.py               # точка входа (uvicorn)
deploy/utriskra-web.service
```

Каталог `runners/` и старые сервисы удалены — все 15 задач работают через
пайплайн (`core/pipeline.py`). Из `services/` остались только обёртки,
используемые провайдерами: midjourney, kandinsky, yandex, qwen_chat.
